# 毫秒悬浮时钟 · 深度优化方案 v2

> 调研时间：2026-11-16
> 基线版本：v1.3（versionCode 4）
> 方法：全网检索 + 国际标准对照（RFC 5905 / Android 官方文档）+ 真机实测（OPPO PEYM00 / Android 13）
>
> **一句话结论**：v1.3 的校时精度已经接近手机网络校时的物理极限（±10ms 量级），
> 继续抠算法收益递减。**剩余价值不在"更准"，而在"更稳、更可诊断、更省心"。**

---

## 一、本次实测的三个关键事实

### 事实 1：用户报的"同步都失败了"，根因是设备没联网

```
wifi_on=0                        # WiFi 关闭
mDataRegState=OUT_OF_SERVICE     # 无 SIM 服务
Active default network: none     # 无任何活动网络
```

开启 WiFi 后立刻恢复，14 源全部成功：

```
校时: 淘宝 -63±25ms; 天猫 -59±24ms; 京东 -77±60ms; 美团 -79±73ms;
      饿了么 -14±91ms; 唯品会 -28±73ms; 拼多多 -48±70ms; 哔哩哔哩 +26±117ms;
      快手 -38±62ms; 小红书 -34±66ms; 支付宝 -64±60ms; 12306 -65±104ms;
      云闪付 -51±34ms; 阿里云NTP -58±22ms;
校时总耗时 3892ms (全量)
```

**代码没错，但产品表达有缺口**：无网时仍会跑满 14 个源、空转 6 秒，
最后给一句和"接口挂了"完全一样的"同步失败，请检查网络"。

### 事实 2：60 秒内，测量噪声是晶振漂移的 3 倍

连续三次快校（间隔 60s）的 NTP 偏移：

```
19:37  阿里云NTP -62±30ms
19:38  阿里云NTP -53±30ms
19:39  阿里云NTP -58±25ms
```

- 三次标准差 ≈ **4.5ms**（随机测量噪声）
- 60 秒内 ±25ppm 晶振漂移 ≈ **1.5ms**（系统性误差）

**这条数据直接决定了优先级**：在当前 60s 快校节奏下，做晶振频率补偿（drift）
的收益会被噪声完全淹没。真正让毫秒位"跳一下"的是噪声，不是晶振。
所以本方案把"抗抖动"排在"drift 补偿"前面——这和直觉相反，但是数据说的。

### 事实 3：系统级时间源可用，但不能当主力

`dumpsys time_detector` 显示：

```
mEnvironment.autoOriginPriorities()=[network,telephony]
Network suggestion history:
  0@PT22.363S   ... Origin: NetworkTimeUpdateService
  1@PT18H1M47S  ... Origin: NetworkTimeUpdateService
  2@PT36H5M0S   ... Origin: NetworkTimeUpdateService
Gnss suggestion history:
  {Empty}
```

- 系统网络时间**确实在工作**，但同步间隔约 **18 小时**——时效远不如本项目的 60s 快校，
  只能当"交叉验证源"。
- **GNSS 授时历史为空**（室内无信号）。GNSS 源必须设计成"取不到就静默跳过"。

## 三、剩余优化点

### P0-1　无网预检：别跑注定失败的 14 个源

**问题**
诊断信息本身已经够用（弹窗 + 明细 + 单源原因）。真正的缺口：

- 无网时仍跑满 14 源，全量空转约 **6 秒**（`deadline = now + 6000`）才给结论。
- "没网"和"接口挂了"文案相同，用户不知道该去开 WiFi 还是等接口恢复。

**方案**
1. 校时前网络预检：
   ```java
   Network n = cm.getActiveNetwork();
   NetworkCapabilities caps = cm.getNetworkCapabilities(n);
   boolean online = caps != null
           && caps.hasCapability(NET_CAPABILITY_INTERNET)
           && caps.hasCapability(NET_CAPABILITY_VALIDATED);   // 关键：VALIDATED 才是真能上网
   ```
   无网直接返回 `ok=false, reason=NO_NETWORK`，**不发任何请求，0ms 出结论**。
2. `NetworkCallback` 补 `onLost()`：断网瞬间把状态行改为"未连接网络"。
3. 状态行文案分级：
   | 场景 | 文案 |
   |---|---|
   | 无活动网络 | `未连接网络 · 点击去设置` |
   | 有网但全部超时 | `14 源全部超时 · 网络可能被限制` |
   | 多数 DNS 失败 | `域名解析失败 · 检查 DNS/VPN` |
   | 多数 SSL 失败 | `SSL 握手失败 · 检查代理/证书` |
   | 部分成功 | `已同步 9/14 源`（现有） |

**收益**：无网场景省 6 秒空转；用户能立刻知道该干什么。
**成本**：小（约 80 行）。
**依据**：Android 官方 Connectivity 文档——`NET_CAPABILITY_VALIDATED` 才代表"实际可达公网"，
只看 `INTERNET` 会把连上了但需要认证的 WiFi 误判为可用。

### P0-2　Doze / 待机下的无效校时

**问题**
`enterScreenOff()` 只处理"屏幕熄灭"，没处理 **Doze（设备空闲）**。
Doze 下网络被系统挂起，校时必然全部超时，还会累加 `failStreak` 触发退避，
导致用户亮屏后反而要等退避时间才能校。

**方案**
```java
PowerManager pm = (PowerManager) getSystemService(Context.POWER_SERVICE);
if (pm != null && pm.isDeviceIdleMode() && !full) return;   // 空闲态跳过快校
```
失败时若处于 idle，不累加 `failStreak`。
**依据**：Android Doze 官方文档——idle 状态下应用网络访问被延迟，此时校时无意义。
**成本**：约 20 行。

### P1-1　校时结果直接覆盖基准，毫秒位会随噪声跳变

**问题**
`applyResult()` 每次都用新结果覆盖 `baseServerMs`。
上一轮 unc=25ms、这一轮 unc=30ms，结果差 8ms，悬浮窗就整体平移 8ms——
盯着毫秒位能看到明显的"跳一下"。这是当前**最容易被用户感知**的精度问题。

**方案：置信度加权融合（RFC 5905 clock discipline 的简化版）**
```java
double delta  = newOffset - currentOffset;
double sigma  = Math.sqrt(prevUnc*prevUnc + newUnc*newUnc);
if (Math.abs(delta) > 3 * sigma) {
    adopt(newOffset);                       // 超 3σ：真实跳变，立即采纳
} else {
    double w = (prevUnc*prevUnc) / (prevUnc*prevUnc + newUnc*newUnc);
    adopt(currentOffset + w * delta);       // 正常噪声：按不确定度加权
}
```
**收益**：显示抖动从 ±8ms 降到 ±2~3ms；同时保留对真实跳变（刚联网、系统时间被改）的敏感性。
**成本**：小（约 40 行 + 单测）。
**依据**：RFC 5905 §11.3 clock discipline 就是用 PLL/FLL 滤波，而不是直接采纳测量值。

### P1-2　时间源没有健康度记忆

**问题**
快校固定用 `taobao / tmall / ntp`。若某个接口变更或当前网络对它不友好，
快校会持续失败，而其他 11 个源其实是好的。

**方案**
- 每源维护 `RingBuffer(20)`：成功/失败、最近 unc、最近 rtt
- 快校选源：**健康度排序取前 3**，健康度 = 成功率 × (1 / 中位 unc)
- 连续失败 3 次的源指数退避（30s → 60s → 120s，上限 10min）
- 时间源页显示每源"近 20 次成功率"

**收益**：弱网/接口变更时快校成功率提升；用户能看到哪个源不稳定。
**成本**：中（约 100 行 + 持久化）。

---

### P1-3　系统级可信时间源（GNSS / 系统网络时间）

**问题**
Android 提供两条**不需要自己发网络请求**的可信时间通道，项目完全没用：

| API | 最低版本 | 精度 | 特点 |
|---|---|---|---|
| `SystemClock.currentGnssTimeClock()` | API 29 | 室外 µs 级 | 无网络也能用 |
| `SystemClock.currentNetworkTimeClock()` | API 33 | 系统 NTP/NITZ | 免自建连接 |

已在 android-34 SDK 确认两个方法存在；测试机 Android 13 满足条件。

**方案**
新增 `gnss`、`sysnet` 两个源：
```java
try {
    long t = SystemClock.currentGnssTimeClock().millis();
    // 与 elapsedRealtime 配对得到 offset
} catch (Throwable ignored) {
    // 无 GNSS 信号时该 Clock 会抛异常，按"跳过"处理
}
```
- 仅当 `SDK_INT >= 29 / 33` 时显示
- **GNSS 源失败不计入 okCount、不触发退避**（室内常态失败，属正常）
- 成功时 unc 给 5ms（GNSS）/ 50ms（系统网络时间）

**收益**：室外多一个 µs 级基准；系统网络时间是独立于自建 HTTP 的交叉验证。
**成本**：小（约 60 行）。
**风险**：部分 ROM 可能抛 `UnsupportedOperationException`，必须 try-catch。
**注意**：由事实 3 可知，系统网络时间 18 小时才同步一次，**不能当主力**。

### P1-4　频率偏差（drift）补偿：长间隔场景的保险

**问题**
走时是纯线性外推：

```java
// FloatingClockService.java:463
long wall = (long) baseServerMs + (SystemClock.elapsedRealtime() - baseElapsed);
```

它假设晶振绝对准确。实际 ±10~30ppm，熄屏 8 小时后可累积 **288~864ms**，
亮屏首帧是错的，要等 `leaveScreenOff()` 那次快校回来（150~400ms）才修正。

**方案**
1. 每次成功校时记录 `(elapsed_i, offset_i, unc_i)`，保留最近 8 条
2. 加权最小二乘拟合 `offset = a + b·elapsed`，**b 即频偏（ppm = b×1e6）**
3. 走时改为 `wall = baseServerMs + dt * (1.0 + drift)`
4. 保护条件（缺一即置 drift=0）：样本 ≥3、跨度 ≥120s、`|drift| ≤ 100ppm`、拟合残差 RMS ≤15ms
5. 平滑更新（新值权重 0.3），避免抖动

**收益（诚实边界）**
| 场景 | 现在 | 加 drift 后 | 是否值得 |
|---|---|---|---|
| 60s 快校间隔内 | 噪声主导 ±5ms | 仍是 ±5ms | ❌ 收益为零 |
| 熄屏 8h 后亮屏 | ±300~900ms，等校时 | ±20~60ms，首帧即准 | ✅ 主要收益 |
| 弱网长时间无法校时 | 持续累积 | 斜率降一个量级 | ✅ 次要收益 |

**结论**：drift 不是为了提升稳态精度（那由 P1-1 负责），而是**缩短"长时间无法校时"后的错误窗口**。
**成本**：中（约 120 行 + 单测）。
**依据**：RFC 5905 §4 时间演进模型含频率偏差项 `R(t0)`；chrony/ntpd 的核心就是维护 freq。

### P2-1　精度趋势可视化

**问题**
用户只能看到"当前 -58ms"，看不到"稳不稳"；排障也没有历史数据。

**方案**
- 记录最近 30 次校时 `(时间, offset, unc, okCount, 耗时)`
- 时间源页底部加迷你折线图（自绘 Canvas，无需第三方库）：offset 曲线 + unc 阴影带
- 长按可导出文本，便于排障

**收益**：把"感觉不准"变成"看得见的稳定性"。同类产品（浮动时间）有类似的"延迟观察"。
**成本**：中。

---

### P2-2　悬浮窗长按菜单

**问题**
现在"长按 1 秒关闭"容易误触——想拖动时稍按久一点就把钟关了。

**方案**
长按弹小菜单：关闭 / 切换毫秒 / 立即校时 / 锁定位置。
**成本**：小。

---

### P2-3　NTP clock filter（严谨性，收益有限）

**问题**
`ntpOnce()` 每台服务器只发 1 次请求，`unc = rtt/2`。单次 RTT 无法反映抖动。

**方案（RFC 5905 §10 简化版）**
每源采 4 样本（间隔 150ms，3 台并行不增加总时长），按 **delay 升序**取最优，
`jitter = RMS(相邻 offset 差)`，最终 `unc = max(rtt_min/2, jitter, 5ms)`。

**收益**：unc 更接近真实误差，加权合成时"假精确"的源不会主导。
**成本**：中（NTP 请求 ×4）。
**说明**：这提升的是"置信度标注的准确性"，不是"实际偏差"——所以排 P2。

## 五、不建议做的事（避免过度工程）

| 想法 | 不做的理由 |
|---|---|
| 完整实现 RFC 5905 intersection + cluster + combine | 14 源 + 中位数降权已覆盖其 90% 收益，复杂度不成比例 |
| 引入 PTP（IEEE 1588） | 移动网络与 Android 应用层均不支持硬件时间戳 |
| 120Hz 渲染 | 功耗翻倍；60fps 下毫秒位已无法逐帧辨认 |
| 自建 NTP 服务器 | 运维成本高；公共源 + 多源合成已足够 |
| 1 秒一次的高频校时 | 耗电与流量代价远超收益；60s 快校 + P1-1 融合已够 |
| 追平 ±1ms 精度 | 公网路径不对称带来的误差就有 ±5~15ms，算法无法突破物理极限 |

## 八、落地结果（v1.4 实测）

P0-1、P0-2、P1-1、P1-2、P1-3、P1-4 六项已全部落地，单测 33/33 通过。
以下是真机（OPPO PEYM00 / Android 13）上的实测记录，含**未达预期**的部分。

### 8.1 无网预检：生效，但"省 6 秒"被高估

```
19:59:35  同步行 同步失败，请检查网络      ← 服务启动 500ms 后的首轮快校
19:59:42  网络预检: 无活动网络
19:59:42  无活动网络，跳过校时
19:59:42  同步行 未连接网络                ← 最终状态正确
```

两个发现：
- **收益被高估**：无网时 Socket 本来就立即报错，首轮快校只花了 **14ms** 就全部失败，
  并不是我原以为的 6 秒空转。预检的真实价值是**文案正确**（"未连接网络"而不是"同步失败"），
  以及省掉 16 个源的线程调度开销。
- **启动瞬间会误判**：服务启动 150ms 时 `ConnectivityManager` 的网络状态还没更新完，
  预检误判为"有网"。已把启动快校延迟从 150ms 改为 **500ms**，给系统状态更新时间。

### 8.2 系统网络时间：实测偏差 -434ms，剔除逻辑必须存在

```
源耗时 系统网络时间 5ms ok
校时: ... 系统网络时间 -434±50ms;
可选源剔除(偏差357ms): 系统网络时间
```

系统网络时间比 14 个网络源的中位数偏了 **-434ms**（Android 每约 18 小时才同步一次）。
如果不做剔除，它会以 150ms 的 unc 拿到不低的权重，把合成值整体拉偏几十毫秒。
**这条实测直接证明了"给可选源加 200ms 偏差剔除"不是防御性编程，而是必需项。**

GNSS 在室内始终返回"无有效响应"，按可选源静默跳过，不影响 `已同步 x/y` 计数。

### 8.3 置信度融合：工作正常，公式与实测完全吻合

```
融合: 实测-39.8  → 基准-71.6 (unc 60/80)
融合: 实测-104.5 → 基准-84.7 (unc 76/60)
融合: 实测-104.5 → 基准-96.9 (unc 60/76)
```

手算校验第二轮：σ=√(60²+76²)=96.8，|−104.5+71.6|=32.9 < 3σ；
w_new = (1/5776)/(1/3600+1/5776) = 0.384 → 触下限 0.4 → 结果 −71.6+0.4×(−32.9) = **−84.76**，
与日志 −84.7 一致。

**调参记录**：下限最初设 0.4，实测发现源质量差时单轮差异可达 65ms，0.4 权重需要 3 轮才收敛。
已提高到 **0.5**，两轮即可跟上真实漂移。

### 8.4 drift 补偿：噪声大时自动弃用（这是正确行为）

```
drift 弃用: -382.5ppm 残差22.1ms (样本4)
```

4 个样本拟合出 -382.5ppm、残差 22.1ms，被保护条件（|ppm|>100 且 残差>15ms）拒绝。
**这不是 bug，而是设计目标**：当前网络噪声（单轮 offset 波动 30~65ms）远大于晶振漂移，
拟合出的斜率必然是噪声的产物。宁可不补偿，也不能用假斜率把走时带偏。

由此得出一个更保守的结论：**drift 补偿只在网络稳定、跨度足够长（≥10 分钟）时才会真正生效**，
它本质上是"熄屏/弱网"场景的保险，不是日常精度的提升手段。这与第 1 节的判断一致。

### 8.5 顺带修掉的一个隐患

drift 更新会改变走时斜率，`dt` 越大跳得越狠（10 分钟 × 5ppm ≈ 3ms）。
已加：变化超过 2ppm 时用旧斜率算出当前时刻并重锚，保证显示连续。

### 8.6 未落地的项

| 项 | 原因 |
|---|---|
| P2-1 精度趋势图 | 需要自绘图表 + 历史持久化，工作量大于本轮其余项之和，价值中等 |
| P2-2 长按菜单 | Service 内弹菜单需额外 overlay 窗口与主题，误触风险可由"长按 1s"文案缓解 |
| P2-3 NTP clock filter | 只提升 unc 标注的准确性，不改变实际偏差 |
