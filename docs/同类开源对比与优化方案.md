# msclock 同类开源对比与优化方案

- 调研时间：2026-11-16
- 调研对象：`github.com/45944831/msclock`（v1.2，提交 `34d8690`）
- 方法：GitHub 搜索 API（中英文关键词）+ 逐仓库 README / 核心源码核对 + 本地全量代码评审

---

## 一、结论摘要

1. **同类开源整体质量偏低**。直接做“Android 悬浮毫秒时钟”的公开仓库约 10 个，绝大多数为 0–3★、2026 年新建的个人项目；唯一成熟的是校时库 `instacart/truetime-android`（1467★ / 195 fork / Apache-2.0），但它只是库，不是悬浮时钟 App。
2. **msclock 在校时维度处于第一梯队**：14 源混合、单调钟+一次性 gap 换算、NTP 四时间戳、HTTP Date 区间交集、CDN 缓存前置检测——这些是本次对比中**没有任何一个同类项目同时具备**的能力。TrueTime / MuTime 只做 NTP，其余悬浮时钟项目要么用系统时间、要么单 NTP 源。
3. **差距主要在“工程化”和“产品体验”**，不在校时算法：竞品已普遍采用 Gradle/CI、Compose/MVVM、DataStore、功能丰富的交互（PiP、事件提醒、毛玻璃、边缘磁吸、捏合缩放）；msclock 是手工 aapt2 构建链、纯 Java 单 Activity 巨型类、无 CI。
4. **结合上一轮代码评审，优先级最高的不是“加功能”，而是修复 3 个已确认的实现缺陷**（±2s 兜底未删、缓存检测可绕过、调度层仍用墙钟），再借鉴竞品做工程化与体验增强。

### 关键差距解读

- **校时严谨性**：TrueTime 校验 `rootDelay` / `rootDispersion` / `serverResponseDelay`（过滤高抖动/未同步服务器），msclock 只校验 mode=4、LI≠3、stratum 1..15。msclock 的 NTP 链在遇到“字段合法但根延迟很大”的服务器时会照收。这是可补齐的确定性差距。
- **缓存抗改钟**：msclock 的 `loadPrefs` 用 `age = wall - savedWall`（墙钟）判 24h 有效期，虽然另有 `clockChanged` 检测（>2s 判失效），但小幅度改钟（如用户把表调快 5 分钟用于“打卡”）会同时让 `age` 失真；MuTime 的思路是缓存只认 `elapsedRealtime`，重启/改钟单独处理，更稳。
- **渲染功耗**：这是最大可优化项。msclock 无论是否显示毫秒，都用 Choreographer 跑 30fps 常驻帧循环，README 自承“单核约 47%”。Apple-Floating-Clock 的“非毫秒模式每秒唤醒一次、不启 VSync”是现成可抄的分级策略——**用户 99% 时间不需要毫秒刷新**。
- **工程化**：msclock 手工 aapt2/d8/apksigner 构建，无 Gradle、无 CI；竞品普遍有 CI、签名配置、分层架构。这不改变功能，但影响可维护性和贡献门槛。

## 四、优化方案（按优先级）

### P0 — 先修正确性（来自上一轮代码评审，最高优先）

1. **删除 `finalizeResult()` 中的 ±2s NTP 硬剔除**（`TimeSync.java:305-317`）
   - 与 CHANGELOG v1.2“不再依赖 ±2s 兜底”矛盾，且会重新引入“单点 NTP 误杀好源”。
   - 若要保留兜底，改为“降权”而非 `p.ok = false`：把该源 unc 乘一个大系数（如 ×8），让 1/unc² 权重自然衰减。

2. **修复缓存检测绕过**（`TimeSync.java:543`）
   - 现状：`allSame && n >= 8`，慢站点 5s 内只采到 3–7 样本时会绕过，带窄交集假收敛返回。
   - 改法：以跨秒事实为准——`if (allSame && span > 1500)` 就判缓存失败，不再看 `n`；`n` 只用于 `n<3` 的最低样本数底线。

3. **校时调度层换单调钟**（`TimeSync.java:212`、`:243`、`:247`）
   - `tStart` / `deadline` / `wait` 改用 `SystemClock.elapsedRealtime()`，否则校时中途跳钟会造成假“响应超时”。

### P1 — 借鉴竞品补齐校时严谨性

4. **NTP 增加 rootDelay / rootDispersion / serverResponseDelay 校验**
   - 参照 TrueTime `TrueTimeParameters`：`rootDelayMax` / `rootDispersionMax` / `serverResponseDelayMax`，从 NTP 包 offset 4/8/16 读取（RFC5905）。
   - 收益：过滤“字段合法但网络质量差”的服务器，减少离群源。

5. **NTP pool 多 IP 展开 + 中位聚合**
   - 参照 TrueTime/MuTime：`InetAddress.getAllByName(host)` 拿全部 IP，各发 1–2 包，取最小 RTT，再对多结果取中位 offset。
   - 收益：当前“阿里云→腾讯→cn.ntp”是**串行接力**（失败才换），改为**并行多 IP + 中位**可同时提升鲁棒性与精度，且不增加墙钟耗时。

6. **缓存持久化改用 elapsedRealtime 锚定**
   - 参照 MuTime：保存 `(syncOffset, syncElapsed, bootEpoch)`；有效性用 `elapsed - savedElapsed` 判定，重启（elapsed 回退）或 `|(wall-elapsed)-(savedWall-savedElapsed)| > 2s` 时失效。
   - 现有 `clockChanged` 检测可保留，但把 `age` 从墙钟改为单调钟，避免小步改钟导致缓存误用。

### P2 — 借鉴竞品做功耗与体验

7. **分级渲染调度（收益最大）**
   - 参照 Apple-Floating-Clock：
     - 非“毫秒开启”场景：每秒对齐到整秒唤醒一次 `invalidate()`，不注册 Choreographer 帧回调。
     - 毫秒场景才启用现有 30/60fps Choreographer。
     - 熄屏继续完全暂停（已有）。
   - 预期：默认场景单核占用从 ~47% 降到接近 0–2%，显著改善续航与发热。
   - 需要新增一个“毫秒显示开关”（默认关，抢购时一键开），与 Apple-FC / 商业产品“按需毫秒”一致。

8. **交互增强（可选，按成本排序）**
   - 边缘磁吸、双指捏合缩放：纯 View 层手势，成本低。
   - PiP 模式 / 事件倒计时提醒：参照 FloatingClockTiming，成本高，需评估是否符合“极简”定位。

### P3 — 工程化

9. **引入 Gradle + GitHub Actions**
   - 保留 `build_apk.sh` 作为无 Gradle 兜底；新增 Gradle 构建与 CI 做编译校验 + 单测。
   - 把 `TimeSync` 的纯算法（区间交集、加权、NTP 解析）抽成可 JVM 单测的类，补边界测试（跳钟、缓存、离群）。

10. **拆分巨型类**
    - `MainActivity`（41K）拆为设置/时间源/校时状态三个 Fragment 或 Compose 页面；`FloatingClockService`（35K）拆出 `TimeAnchor`、`OverlayController`、`SyncScheduler`。
    - 非功能刚需，但决定后续能否持续迭代。

## 五、建议实施顺序

| 阶段 | 内容 | 验证方式 |
|---|---|---|
| 第 1 步 | P0 三项修复 | 单源/全量校时回归；构造跳钟与慢站点 case |
| 第 2 步 | P1.4 + P1.6（NTP 校验、缓存锚定） | 与 TrueTime 并跑对比 offset；改钟/重启测试 |
| 第 3 步 | P2.7 分级渲染 | 真机 `dumpsys cpuinfo` 对比默认场景 CPU |
| 第 4 步 | P1.5 + P3（并行 NTP、Gradle/CI、拆类） | CI 全绿；真机 132 项脚本复跑 |
