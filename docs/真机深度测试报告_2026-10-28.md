  - **常驻渲染成本下降**：默认 30fps 后前台 **46.7–48.0%**、桌面背景 **31–37%** 单核（60fps 为 50–75%）；

  - **熄屏开销**：熄屏暂停渲染与周期校时，实测 **0.00–0.05%**（原 1.45–2.80%）；
  - **失败弹窗**：后台重校成功自动关闭，失败明细不再残留；
  - **外部指令**：启停入口改为 `DUMP` 权限守卫的 `CmdReceiver`，普通应用无法启停；
  - **无权限通知**：不再先弹前台通知再退出。

## 二、已实施的优化（本轮代码）

### 1. 悬浮窗渲染循环重写

| 改动 | 位置 | 效果 |
|---|---|---|
| 单帧 Choreographer 回调替代 16ms `postInvalidateOnAnimation` | `FloatingClockService.java:388-402` | 帧节流可控，无空转 |
| 帧间隔 30fps 默认、可切 60fps，2ms vsync 容差 | `FloatingClockService.java:110,181-183,396` | 默认功耗下降，60fps 仍可选 |
| 窗口显式 `FLAG_HARDWARE_ACCELERATED` | `FloatingClockService.java:459` | 服务窗口改走 HWUI，降低软件绘制开销 |
| 移除 `FLAG_LAYOUT_NO_LIMITS`，绘制去 subpixel | `FloatingClockService.java:458`、`ClockView.java:53,56` | 避免越界布局与逐帧抗锯齿成本 |
| 零分配 `drawText(char[])` 绘制 | `ClockView.java:133-134` | 每帧不再生成格式化字符串 |

### 2. 校时分层与线程治理

- 快校 **3 源 / 60s**、全量 **14 源 / 10min**、切换源即单源重校（`FloatingClockService.java:406-421`）。
- 失败退避 60s → 最长 10min（`:291-295`）；网络恢复回调立即重校（`:518-535`）。
- 14 线程 `join(11s)` 改为 **4 线程池**（核心线程 30s 空闲回收）+ 单线程扫描执行器（`TimeSync.java:71-80`）。
- 扫描代次 `scanSeq` 防止旧轮次结果污染进度（`TimeSync.java:67,215,223`），进度计数原子化。

### 3. 状态持久化

- scale / alpha / fps / source / manual / posX / posY（`FloatingClockService.java:103-114,225-227,267,644`）。
- 校时缓存（偏移 + 来源 + 墙钟）24h 内复用，冷启动首帧即准（`:120-132`）。

### 4. 边界与交互

- 拖动与缩放后统一钳制在屏幕内（`FloatingClockService.java:603-618`），拖动结束落盘（`:577,639-645`）。
- 最大缩放按**基准内容尺寸**计算并受屏幕宽高约束（`:620-635`，`ClockView.java:73-80`），修复连续拖动滑杆时 200% 越界。
- 默认位置为右上（x 右对齐、y=120dp），不再压住设置页“大小”滑杆。

### 5. 生命周期与权限

- 权限看门狗：每 64 帧检查 `Settings.canDrawOverlays`，撤销即退出服务（`FloatingClockService.java:391-393`），主界面状态随之归零。
- 主界面 200ms 刷新在 `onStop` 停止、`onStart` 恢复（`MainActivity.java:86,113-122`），退后台不再空转。

| 5 | 无权限时仍先 `startForeground` 再 `stopSelf`，通知闪现 | 先判权限再建通知；仅 `startForegroundService` 拉起时满足 5s 义务后立即撤销（`FloatingClockService.java:436-451`） | P07/P08 通过，无崩溃、无残留通知 |

### 5.2 仍存在的限制（非缺陷或 OEM 策略）

1. **ColorOS 上划清任务强停（C04，WARN，不可完全规避）**
   - 现象：最近任务上划后系统 `force-stop`，服务/窗口/通知全部清理，`START_STICKY` 不生效。
   - 建议：首次开启时引导加入“自启动/后台运行白名单”；属 OEM 策略，代码层无法强制存活（README/更新记录已说明）。

2. **常驻渲染成本仍偏高（30fps 约 48% 单核）**
   - 原因：该 ColorOS 设备每次覆盖层合成约 7ms（RenderThread），与内容复杂度弱相关；已通过 30fps 默认 + 硬件加速 + 去 subpixel 降低约 30%。
   - 建议（如需进一步降耗）：静止时降频（秒变化才全量刷新，毫秒区域局部脏刷新）；或提供“省电模式（15fps）”。60fps 仍保留供高刷需求。

## 六、测试方法与限制

1. 坐标为 1080×2400 真机像素；截图经助手侧等比显示，点击均按真机坐标下发。
2. ColorOS 禁止 shell `appops set`（uid 2000 无 `MANAGE_APP_OPS_MODES`），权限变更统一通过系统设置页开关完成（坐标 1037,936）；这也是权限撤销类用例改用 UI 操作的原因。
3. CPU 为单核百分比（8 核设备），来自 `/proc/<pid>/stat` 采样并与 `top`/`dumpsys cpuinfo` 交叉验证；30s/20s 窗口会包含周期性校时开销，故前台 CPU 为区间值。
4. 设备上存在 WeakNet 等第三方应用会周期性抢占前台，测试前统一 force-stop；所有安装均为覆盖安装，未动用户数据。
5. 测试脚本自身问题已修正并复跑（非产品缺陷）：红色主按钮锚点、悬浮窗盖住滑杆导致点击被消费、天猫品牌色断言、ROM 日志噪声被误判为应用错误、断网恢复未等真实联网。修正后相关用例全部通过。
6. 发布版回归：自动化启停由 `am start --es cmd` 改为 `am broadcast -a com.wb.msclock.action.CMD -n com.wb.msclock/.CmdReceiver --receiver-include-background`（对应第 5.1 节第 4 项的安全修复）；8 组用例全部复跑，结果 132 项 PASS 131 / WARN 1 / FAIL 0。
